### 1. Vercel 이중 빌드 경로

Vercel에 연결된 프로젝트는 **두 가지 경로**로 동시에 빌드될 수 있다.

| 경로                      | 트리거                | 실행 위치       | CLI 버전           |
| ------------------------- | --------------------- | --------------- | ------------------ |
| GitHub Actions 워크플로우 | `push` (e.g. dev)     | Actions runner  | 우리가 명시한 버전 |
| Vercel Git 통합           | PR 열림 / 브랜치 push | Vercel 클라우드 | Vercel이 자동선택  |

**식별 방법**: 로그의 `Vercel CLI X.Y.Z` 버전 차이로 구분 가능.

**오늘의 케이스**:

- GitHub Actions 로그(`Vercel CLI 50.13.2`)는 dev 머지 후 빌드 성공 → 마지막 `vercel deploy --prebuilt` 업로드에서 Vercel API 5xx(`Internal S...`)
- Vercel Git 통합 로그(`Vercel CLI 54.4.1`)는 `feat/sentry-setup` 브랜치의 옛 커밋(`7c4b451`)을 자체 빌드 → sentry 버전 충돌로 실패

→ **두 로그를 헷갈리지 말 것**: 브랜치명·커밋 SHA·CLI 버전으로 구분.

### 2. Sentry Capacitor의 형제 패키지 검증

`@sentry/capacitor` 설치 시 `scripts/check-siblings.js`가 postinstall로 실행되며, `@sentry/nextjs`/`@sentry/react` 등의 버전이 정확히 매칭되지 않으면 빌드를 막는다.

```text

npm error Please install the mentioned packages exactly with version 10.43.0

```

**해결 패턴**: 캐럿 없이 정확 버전 고정.

```json

  "@sentry/nextjs": "10.43.0" // 캐럿(^) 금지
}
```

Dependabot 같은 자동 PR이 마이너 업그레이드를 시도하면 다시 깨지므로, 두 패키지는 묶어서 업데이트해야 함.

### 3. CSS `overflow-x-auto`의 숨은 Y축 잘림

```css
.container {
  overflow-x: auto;
  /* overflow-y는 명시 안 했으니 visible? — 아니다 */
}
```

**CSS 사양**: `overflow-x`와 `overflow-y` 중 하나라도 `visible`이 아니면, 다른 한 쪽이 `visible`이어도 **자동으로 `auto`로 변환된다**.

→ `overflow-x-auto` 컨테이너 안에서 `-top-2`로 튀어나온 자식은 위쪽도 잘림.

**해결**: 튀어나온 만큼의 패딩 확보.

```tsx
<div className="flex gap-3 overflow-x-auto pt-2 pr-3 last:pr-0">
  {items.map((item) => (
    <div className="relative w-16 h-16">
      <img ... />
      <button className="absolute -top-2 -right-2 ...">×</button>
    </div>
  ))}
</div>
```

### 4. Spring Boot 500의 진짜 의미

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)    // → 400/404 등
    @ExceptionHandler(MethodArgumentNotValidException.class)  // → 400 (validation)
    @ExceptionHandler(MaxUploadSizeExceededException.class)   // → 413
    // ...
    @ExceptionHandler(Exception.class)             // → 500 fallback
    protected ResponseEntity<...> handleException(Exception e) {
        log.error("Unhandled exception: ", e);
        return ...INTERNAL_SERVER_ERROR;
    }
}
```

500("서버 내부 오류가 발생했습니다")이 뜨면 = **검증 실패가 아니라 코드가 예상 못한 RuntimeException**. 백엔드 로그의 `Unhandled exception:` 스택트레이스가 진짜 원인.

가능한 유형:

- DB 제약 위반 (`SQLIntegrityConstraintViolationException`)
- NPE
- 인증 컨텍스트 누락 (`securityUtil.getCurrentUserId()` null)
- Jackson deserialization 예외

### 5. FE/BE 스키마 + DB 마이그레이션 동기 불일치

코드 레벨 스키마는 동기화돼도 **운영 DB에 마이그레이션이 누락**되면 INSERT 시점에 터진다.

```text
백엔드 PR: title 컬럼 제거 + DB 마이그레이션 필요(ALTER TABLE posts DROP COLUMN title)
프론트:    title 필드 여전히 전송
운영 DB:   title NOT NULL 컬럼 그대로

→ FE 요청 → BE는 title 무시 → INSERT 시 title=null
→ NOT NULL constraint violation → SQLException → 500
```

**체크리스트**:

1. 백엔드 PR description에 "DB 마이그레이션 필요" 명시되어 있는지
2. 프로덕션 DB에 적용됐는지 (Flyway/Liquibase 로그, 또는 수동 ALTER 수행 여부)
3. FE 측 요청 스키마도 함께 동기화

### 6. iOS Capacitor 키보드 + viewport 안정화 패턴

textarea가 메인인 페이지에서 키보드가 올라오면 webview의 visual viewport가 변형되면서 헤더가 위로 밀려나는 현상.

**불안정**:

```tsx
<main className="h-safe-viewport ... flex flex-col overflow-hidden">
  <BackHeader />
  <div className="flex-1 ...">
    <textarea />
  </div>
</main>
```

**안정 패턴** (login/nickname, community/write 적용):

```tsx
<div className="relative flex w-full flex-col bg-white overflow-hidden h-safe-viewport">
  <div className="mx-auto flex h-full w-full max-w-[480px] flex-col">
    <BackHeader />
    <div className="flex-1 flex flex-col min-h-0">
      <textarea />
    </div>
  </div>
</div>
```

핵심: **외곽 div가 viewport 잠금** + **내부 wrapper에 `h-full` 강제** → 키보드 동작 시 native scroll이 외곽을 못 뚫음.

`h-safe-viewport` 정의 (`globals.css`):

```css
.h-safe-viewport {
  height: calc(100vh - env(safe-area-inset-top, 0px));
  height: calc(100dvh - env(safe-area-inset-top, 0px));
}
```

### 7. CSS `position: sticky` 동작 조건

흔히 오해하는 점: sticky는 그냥 적용한다고 작동하지 않는다.

**필수 조건**:

1. 가장 가까운 **스크롤 컨테이너(`overflow: auto|scroll`)가 부모** 어딘가에 있어야 함
2. 그 스크롤 컨테이너의 **내부 자식**으로 sticky 요소가 위치해야 함

**깨뜨리는 패턴**:

```tsx
<div className="overflow-hidden">
  {" "}
  {/* 스크롤 불가 → sticky 무효 */}
  <header className="sticky top-0"> ... </header>
  <div>...</div>
</div>
```

**올바른 패턴**:

```tsx
<div className="overflow-y-auto h-screen">
  {" "}
  {/* 스크롤 컨테이너 */}
  <header className="sticky top-0"> ... </header>
  <div className="h-[2000px]">...</div>
</div>
```

→ 현재 `BackHeader`에 `sticky` prop이 있지만 부모가 `overflow-hidden`이면 효과 없음. 구조적 해결이 필요한 이유.
